# Security model and operations

SentinelAuth validates LDAP credentials by binding as the user, and validates service tickets through Java GSS-API under an acceptor-only JAAS subject. Kerberos identities must belong to the exact configured realm and map to a unique directory uid; service and cross-realm principals are rejected. LDAP referrals are not followed. Directory queries have bounds, filter escaping, strict uid syntax, and connection/read timeouts. Group DNs are compared as LDAP names and only two explicit groups map to authorities. A valid identity with no mapped group has no resource access.

The test OpenLDAP reader can read directory metadata but cannot read password hashes. Anonymous users can authenticate but cannot search. Offline `slapadd` bootstraps data; the server has no online directory administrator password. Production directories should use their own audited service account ACLs, uniqueness constraints, lockout policy and password policy overlay.

## Sessions and browser protections

All login and logout POSTs require a session CSRF token. Authentication rotates the session ID and CSRF token. Sessions expire after 15 minutes idle and eight hours absolute age. Cookies are HttpOnly, SameSite=Strict, and Secure by default. Only local Compose disables Secure cookies. Role changes take effect on reauthentication or session expiration; urgent revocation requires deleting that principal's rows from `spring_session`. Session persistence in PostgreSQL supports replicas; protect the database and backups as authentication material. Do not deserialize session rows from an untrusted database.

TLS is mandatory at the ingress, and LDAPS is enforced unless explicitly opted into local plaintext LDAP. The application ignores forwarded headers. Do not expose port 8080 directly in production; configure ingress HTTPS redirection and HSTS. Separate management port 9090 is accessible only to the monitoring namespace through NetworkPolicy. NetworkPolicy requires a CNI that enforces it. Trust the issuing CA for LDAP using the mounted Java truststore; PostgreSQL verifies its CA and hostname using `sslmode=verify-full`. Never disable hostname verification.

## Kerberos operations

Register the public HTTP hostname's SPN exactly, provision its keytab out of band, and mount it with mode 0440 and group 10001. Do not delegate client credentials. Maintain synchronized clocks. Java validates ticket integrity, lifetime and replay. A PostgreSQL unique ledger additionally rejects repeated identical SPNEGO tokens across replicas. This supplemental raw-token ledger does not replace Kerberos authenticator replay protection against differently wrapped tokens; deployments requiring a global authenticator cache must provide an audited shared replay mechanism or terminate SPNEGO at a single security tier. The built-in flow accepts complete Kerberos SPNEGO requests with a mutual-authentication response; incomplete multi-round negotiations, NTLM, credential delegation, cross-realm identity mapping and channel-binding/extended-protection enforcement are outside this implementation. TLS termination must be inside the trusted perimeter.

Rotate HTTP keys by overlapping key versions in the mounted keytab and rolling pods; the JAAS subject is loaded at startup. The example KDC issues one-hour AES tickets and is strictly a development fixture. Never deploy it, its realm, or the local LDAP fixture as an enterprise directory.

## Credentials, database and auditing

No production credentials are committed. Local initialization generates independent random secrets inside a mode-0700 host directory. The generated LDIF and two KDC fixture secrets have mode 0644 so nonroot bind-mounted containers can read them; the private parent directory prevents other host users from traversing to them. Other credentials and `.env` remain mode 0600. The Docker test KDC keytab volume is readable inside containers to allow the nonroot gateway to use it; production mounts are more restrictive. Compose environment variables are inspectable by Docker administrators; use an external secret store and projected secrets in production. The application also supports Spring config-tree files named DATABASE_PASSWORD and LDAP_BIND_PASSWORD under `/run/secrets/`.

Use a schema-owner credential only for migrations, then `deploy/production-grants.sql` for the runtime role and disable application Flyway. The runtime role can append audit and replay rows but cannot update or delete them. An audit write failure prevents session creation and returns 503. Record fields exclude passwords, tokens and keytab bytes; usernames are bounded and validated. Database timestamps and trace identifiers support incident correlation. JSON logs are supplemental to the durable database record; send both to access-controlled retention storage. Storage administrators still have control over the database; use external immutable retention when required. Audit records describe credential decisions before session persistence; a later session write failure may leave a successful credential audit without a usable session.

Schedule privileged retention jobs according to policy. Keep replay records at least 24 hours, longer than ticket/authenticator acceptance windows, and delete expired rows with a maintenance account. Never grant cleanup rights to the runtime role. Bound session serialization volume and monitor database capacity and cleanup. Audit rows contain personal data; restrict access and define retention.

## Abuse controls and operational scope

A bounded per-replica, per-source-address limiter allows 20 credential attempts per minute and returns 429. Since forwarded headers are ignored, an ingress address may aggregate users. Use a trusted ingress/WAF rate limiter with identity-aware and distributed quotas for large deployments. Bounded cache eviction is not a complete distributed brute-force defense. Never blindly trust X-Forwarded-For. Generic 401 bodies avoid direct username disclosure, but LDAP response timing can still vary. Directory outages and audit database outages return 503 without granting access. CSRF failures return 403 before credential processing.

Availability uses Prometheus `up`, HTTP readiness, and a directory-availability gauge updated by readiness checks. Readiness checks the database and directory; liveness only checks the process. A KDC outage prevents clients from obtaining new tickets but need not prevent acceptance of existing valid tickets, so KDC availability is monitored separately. Use external monitoring for TLS expiry, clock drift, KDC ticket issuance, replay failures and audit backlog. Production OTel transport should use authenticated TLS via a local collector or mesh; the test collector prints traces without an external backend.

This gateway supplies enterprise authentication building blocks, not MFA, an OIDC/OAuth authorization server, an account lifecycle system, or a production certification. Perform a deployment-specific threat model and penetration test before exposing it to enterprise users. Report security issues privately to repository maintainers; do not publish credentials or valid tickets in issues.
